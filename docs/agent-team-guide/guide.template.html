What you have today

A complete catalog of specialists, their written instructions, a workflow that requires evidence, and software that saves work and can recover after interruptions.

The 50 roles are installable definitions. They are not 50 background processes. This source checkout does not contain an installed team runtime, and the project records say the supervisor has not had its paid pilot or host activation.

The practical recommendation

6 persistent core responsibilities + 1 supervisor service, with builders, reviewers and other specialists called when their tasks need them.

This is a proposed design, not a discovered deployment or a universal minimum. Persistent state and reliable wake-up matter more than keeping six model sessions open.

Quality cannot be guaranteed across every LLM or harness. A replacement should earn admission through tests and repeated comparisons; otherwise keep the qualified configuration or stop for review.

A small glossary

Role / agent
A job description plus instructions, tools, task ownership and outputs. A session executes that role.
LLM / model
The reasoning engine. Its capability, cost, context window and behavior can change.
Harness
The application that runs the model and connects tools, sessions, permissions and subagents, such as Codex or Claude Code.
Durable
Identity, decisions and work state survive a stopped session or restarted machine, and execution can safely resume when the host is available.
Supervisor
Deterministic software that accepts work, starts workers, tracks attempts and budgets, and holds when human input is required.

Not every task needs the full company

The platform-core preset has 11 roles. The full-company preset exposes all 50, but the 18 specialists are still activated only when needed.

A role can be present without running or consuming model calls. Small work can use a fullstack engineer; larger work can split into backend, frontend, database and domain specialists.

Who has the final authority?

The human owner controls approval decisions. CEO coordinates intent, Delivery Lead coordinates execution, and QA verifies independently. The supervisor can stop and ask; it cannot approve its own work or waive a gate.

Marketing publishes, messaging, ad spend and other external commitments follow the same human gates.

Yes — every agent has a prompt

All 50 canonical role files are included below, exactly as stored in the repository. These are the team's role prompts. Compiled agents also receive shared contracts, protocols and harness-specific settings; a role file alone is not the complete runtime instruction set.

What the instructions contain

Mission, expertise, operating steps, collaboration, guardrails, learning rules and an output contract. The manifest adds access class, model tier, reporting line and capabilities.

The role tells an agent what to do; the CLI checks recorded state; supported harness permissions constrain tool calls. A written rule is not automatically an enforced security boundary.

Access classes

  • read-only: inspect and report.
  • research: inspect plus web research.
  • review: inspect, run checks and record review evidence; no project source edits.
  • workspace-write: edit within assigned work.
  • orchestrate: coordinate and delegate as well as write.

These are intended permissions. Actual enforcement differs by harness; review restrictions are not a universal sandbox.

Seven human-only action groups
  1. Production deployment.
  2. Publishing or contacting real people.
  3. Spending or creating paid resources.
  4. Real credentials and payment operations.
  5. Destructive or production-data operations.
  6. Broad system changes.
  7. Legal commitments.
These remain human-gated even under the unattended profile. A local release-stage exit does not grant production deployment permission.
protocols/guardrails.md; config/policies.json.
What “unattended” actually allows
Reversible, in-scope work can proceed. A run containing only R0–R1 tasks may leave release without a click only with passed checks, independent verification at the current commit, a complete release packet, a successful rollback rehearsal and no unresolved budget checkpoint.
Any R2+ task restores the human release checkpoint. R3/R4 external or sensitive actions remain human-gated.
R0 = inspection · R1 = local reversible changes · R2 = consequential workspace changes · R3 = external effects · R4 = sensitive or irreversible actions.

What survives a harness change?
  • Canonical role definitions and output contracts.
  • Task graph, accepted requirements and recorded evidence.
  • Versioned protocols, policy and reviewed knowledge.
What must be qualified again?
  • Tool schemas, permissions and refusal behavior.
  • Context handling, delegation and output parsing.
  • Cancellation, recovery and duplicate side effects.
  • Usage accounting and budget behavior.
  • Task quality for the new model + harness + tools + prompts.
Shared tool protocols help interoperability. They do not make capabilities or safeguards equivalent.






How many durable agents do you need?
Start with six persistent core responsibilities and one deterministic supervisor. This is a practical architecture recommendation for this repository, not a universal minimum and not an already-deployed team.


Persistent means the role's contracts, decisions, task position and evidence remain available across sessions. Workers can start only when needed and then exit. You do not need six continuously running or continuously billing LLM sessions.




+ One supervisor service
The supervisor owns the durable queue, attempts, leases, checkout reservations, retries, usage accounting and recovery. It is software, not a seventh LLM agent. Authorization and sandbox enforcement must also remain outside model judgment.
One supervisor worker per checkout is the current limit. That worker may delegate task-level work inside the harness, within policy. More simultaneous top-level workers require separate checkouts and safe integration.
scripts/agentic_supervisor.py; docs/supervisor-operator-guide.md:63, :210, :306.
+ Workers when a job needs them
The Product Manager owns acceptance criteria; the CTO designs the solution. Builders implement it; Code Reviewer and QA inspect independently; Release Manager prepares release and rollback. Other specialists join on their triggers.
These roles are still necessary for suitable tasks. “Six core” describes persistent coordination and quality responsibilities, not the total number of people or worker sessions needed to deliver every project.
The proposed persistent responsibilities extend existing role contracts and would need explicit implementation and evaluation.


The quality promise you can actually enforce
Do not promote a replacement configuration unless it meets the agreed quality floor. If it fails, keep the last qualified configuration, use a qualified fallback, or stop. More agents cannot make an incapable model equally capable.

What remains, in order
  1. Fix the documented pre-pilot gaps. Strengthen the isolation proof, explicit credential filtering and host/sandbox path alignment.
  2. Prove a bounded live run. Complete the isolated paid pilot and record independent acceptance, cost, audit and recovery evidence.
  3. Qualify a second model/harness pair. Exercise adapter behavior and real task quality against the same baseline.
  4. Enforce admission and fallback. Reject regressions; keep the qualified configuration and a tested rollback path.
  5. Activate bounded work. Only after the owner authorizes the host task; monitor holds, failures and spend.
Steps 1–2 and owner activation follow the existing pilot plan. Cross-harness qualification and the six-role persistent core are recommendations. This guide performs none of those operational actions.
Improvement without silent drift
Observe a result → record a scoped lesson → propose a playbook check → evaluate it → request human promotion → record the change.
Good lessons survive model changes because they live outside chat memory. Bad lessons and prompt injection should not be promoted merely because a model sounds confident.
The current design deliberately does not let agents silently rewrite their own rules or lower safety gates. “Fully autonomous” here means reliable work within an approved boundary, with escalation outside it.
